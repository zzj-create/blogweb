## 1.项目介绍(项目地址:https://gitcode.com/gcw_PEqEAaI8/ctf-agent)

本项目是一个基于 OpenCode 的 CTF 多 Agent 协作系统，目标是把传统 CTF 比赛中分散、手工、难复盘的流程，整理成一套可调度、可记录、可沉淀的半自动化作战框架。

它不是单纯的“AI 自动解题脚本”，也不是只调用几个工具的命令集合，而是围绕真实 CTF 比赛流程设计的一套系统。项目尝试把登录平台、获取题目、题目分类、分发给不同方向 Agent、回收结构化结果、统一提交 flag、生成 writeup、沉淀知识库这些环节串起来。

整体思路是：由 `ctf-agent` 作为总控，负责比赛状态、题目队列、提交队列和动态环境管理；由 `web-agent`、`pwn-agent`、`reverse-agent`、`crypto-agent`、`misc-agent` 分别处理不同方向题目；由 `wp-agent` 负责赛后 writeup 和知识沉淀。这样可以让每个 Agent 的职责更清晰，避免所有任务都堆给一个通用 Agent。

项目目前更适合定位为“CTF 辅助作战系统”或“多 Agent CTF 协作框架”。它已经具备基础状态机、任务分发、结构化结果回传、统一提交和知识库沉淀能力，但还没有达到完全自动化 CTF 战队的程度。真实测试中，不同平台的登录、拿题、交题仍然不够流畅，多 Agent 并发也还存在等待和效率损失，知识库也需要通过持续比赛和喂题不断完善。

如果从使用价值上看，它主要提升的是 CTF 解题过程中的组织能力、复盘能力和知识复用能力。也就是说，它不保证每道题都能自动解出，但可以让解题过程更标准、更可追踪，并让每一次比赛的经验更容易沉淀到下一次比赛中。

## 2. 项目目标

这个项目的目标不是简单做一个“自动答题脚本”，而是搭建一个面向 CTF 比赛的多 Agent 协作框架。

它希望解决的问题是：

- 比赛中题目多、方向杂，一个 Agent 很难同时稳定处理 Web、Pwn、Reverse、Crypto、Misc。
- 真实比赛流程不只是解题，还包括登录平台、拿题、开环境、提交 flag、整理 writeup、沉淀知识。
- 如果没有统一状态和提交管理，多 Agent 很容易重复提交、抢状态、漏记录、结果不可追踪。
- CTF 解题能力需要长期积累，单次 prompt 很难替代知识库和历史题经验。

所以本项目采用“中心调度 + 专项 Agent + 状态机 + 知识库沉淀”的设计。

## 4. 架构思想

### 4.1 控制面和执行层分离

项目把系统拆成两层。

控制面负责“规则是什么”：

- 哪类题交给哪个 Agent。
- 哪个 Agent 必须加载哪个技能。
- workspace 放在哪里。
- flag 是否允许 specialist 直接提交。
- 动态题最多能开几个环境。
- 赛后 writeup 和知识沉淀应该输出到哪里。

执行层负责“事情怎么落地”：

- 创建比赛状态。
- 读取和写入题目状态。
- 生成 Agent 的任务包。
- 接收 Agent 的结构化结果。
- 管理提交队列。
- 执行赛后总结和知识沉淀。

这种拆分的好处是：规则可以持续调整，执行层只负责稳定执行，不会把所有逻辑都写死在某一个脚本里。

### 4.2 中央调度而不是自由协作

项目中 `ctf-agent` 是全局调度者，其他方向 Agent 只负责解题。

方向 Agent 包括：

- `web-agent`
- `pwn-agent`
- `reverse-agent`
- `crypto-agent`
- `misc-agent`

它们的职责是分析题目、写 notes、写 solve 脚本、给出 flag 和证据。

它们不直接提交 flag。

所有 flag 都必须回到 `ctf-agent`，由统一提交队列处理。这样做虽然牺牲了一点直接性，但能避免重复提交、误提交、并发提交和状态混乱。

### 4.3 用状态机管理比赛过程

真实 CTF 不是一次问答，而是一连串状态变化。

一个题目可能经历：

```text
发现题目 -> 分类 -> 分发 -> 解题 -> 找到 flag -> 等待提交 -> 提交中 -> accepted/rejected/unknown -> writeup -> 知识沉淀
```

动态题还会多出：

```text
启动环境 -> 使用 target -> 提交成功 -> 关闭环境 -> 释放槽位
```

项目用 `state/` 目录保存这些中间状态，避免 Agent 之间只靠自然语言交流导致上下文丢失。

### 4.4 结构化结果优先

方向 Agent 的输出不是一句“我解出来了”，而是一个结构化结果。

结果中通常包括：

- `challenge_id`
- `category`
- `source_agent`
- `status`
- `flag`
- `confidence`
- `evidence`
- `artifacts`
- `workspace_root`

结构化结果的好处是后续可以自动提交、自动写 writeup、自动进入知识库，而不是每次都靠人工复制粘贴。

## 5. 核心设计的原因与优势

### 5.1 为什么要做多 Agent 分工

CTF 不同方向差异很大。Web 更关注协议、框架、鉴权和漏洞链；Pwn 更关注二进制、内存、libc 和利用链；Reverse 更关注反编译、算法和混淆；Crypto 更关注数学和密码结构；Misc 更关注取证、隐写、流量和杂项工具。

如果所有题都交给一个通用 Agent，它需要在多个方向之间频繁切换，容易出现分析浅、工具选择不准、上下文混乱的问题。

多 Agent 分工的优势是：

- 每个 Agent 只专注自己的方向，提示词、工具习惯和知识库都更集中。
- 方向知识可以单独积累，Web 的经验不会和 Crypto、Pwn 混在一起。
- 多个题目可以并行分析，提高比赛中的整体吞吐量。
- 某个方向 Agent 失败时，不会影响其他方向继续推进。

这样设计的核心原因是：CTF 解题能力很大程度来自专业化经验，而不是单个通用模型的平均能力。

### 5.2 为什么需要 `ctf-agent` 做中央调度

如果让每个方向 Agent 自己决定什么时候拿题、什么时候提交、什么时候关闭环境，短期看更自由，但真实比赛中很容易出问题。

可能的问题包括：

- 多个 Agent 重复处理同一道题。
- 多个 Agent 同时提交 flag，触发平台限制或误判。
- 动态环境被重复开启或忘记关闭。
- 某个 Agent 解出题后没有把结果写回统一位置。
- 比赛结束后无法知道哪些题解过、哪些题失败、哪些题需要复盘。

中央调度的优势是：

- 所有题目状态都由一个总控维护。
- flag 提交统一进入队列，避免并发提交和重复提交。
- 动态环境数量可以被统一限制。
- Agent 之间不需要互相协调，只需要按规则交付结果。
- 后续做自动化、监控、恢复和审计更容易。

这样设计的核心原因是：CTF 比赛不是单题问答，而是一个多任务、多状态、多风险的流程，必须有一个总控来保证秩序。

### 5.3 为什么控制面和执行层要分离

控制面负责规则，执行层负责落地。这种设计可以避免项目变成一堆写死逻辑的脚本。

如果不分离，很多规则会直接散落在代码里，例如哪个方向用哪个 Agent、workspace 怎么命名、动态题最多开几个、赛后输出放哪里。后续一改策略，就需要到处改代码。

分离后的优势是：

- 策略变化可以优先改配置和文档，不一定要改核心执行代码。
- 执行层可以保持稳定，专注状态读写、队列、校验和落盘。
- Agent 行为边界更清楚，不容易出现职责重叠。
- 后续接入新平台、新 Agent、新输出格式时扩展性更好。

这样设计的核心原因是：CTF 平台和比赛流程变化很快，系统需要能调整策略，而不是每次都重写执行逻辑。

### 5.4 为什么要用状态机

真实比赛中，一个题目不会只有“未解”和“已解”两个状态。

它可能处于等待分发、正在分析、找到 flag、等待提交、提交失败、提交未知、动态环境关闭失败、等待 writeup、总结失败等状态。

状态机的优势是：

- 可以清楚知道每道题当前卡在哪一步。
- 系统崩溃或中断后，可以从状态文件恢复。
- `ctf-status` 可以给出下一步建议。
- 自动化流程可以根据状态决定继续提交、重试、总结或等待人工处理。
- 赛后复盘时能看到完整路径，而不是只看到最终结果。

这样设计的核心原因是：CTF 自动化最怕“中间过程丢失”，状态机就是为了让过程可追踪、可恢复。

### 5.5 为什么要用结构化结果

自然语言结果对人友好，但对自动化流程不友好。

例如 Agent 说“flag 应该是 flag{xxx}，我觉得能过”，人可以理解，但程序不知道 challenge_id 是什么、置信度是多少、证据在哪里、是否应该提交。

结构化结果的优势是：

- 程序可以自动校验字段是否完整。
- `challenge_id` 明确，不会把结果写到错误题目。
- flag、confidence、evidence、artifacts 可以被后续流程直接使用。
- 可以自动进入提交队列。
- 可以自动作为 writeup 和知识沉淀的输入。

这样设计的核心原因是：只有结构化结果才能让“Agent 解题”和“系统自动提交、总结、沉淀”真正接起来。

### 5.6 为什么 specialist 不能直接提交 flag

让 specialist 直接提交 flag 看起来更快，但风险很高。

真实比赛中，提交通常有次数限制、频率限制、错误惩罚或平台风控。如果多个 Agent 自己提交，很容易出现重复提交、误提交、提交错题和结果不可追踪。

统一提交的优势是：

- 所有 flag 先进入队列，便于去重。
- 同一时间只做一个平台提交，减少并发风险。
- submit_unknown 可以被单独处理，不会被误判为 rejected。
- 动态题可以在 accepted 后再统一关闭环境。
- 提交行为有记录，方便复盘和排障。

这样设计的核心原因是：提交 flag 是比赛中风险最高的动作之一，必须中心化管理。

### 5.7 为什么要限制动态题双槽位

很多 CTF 平台的动态环境资源有限，频繁开启环境可能导致平台限制、资源浪费或管理混乱。

双槽位设计的优势是：

- 控制同时运行的动态环境数量。
- 默认保留 Web 和 Pwn 两类最常见动态环境槽位。
- 避免一口气开太多环境导致 target、端口、容器状态混乱。
- accepted 后再关闭并释放槽位，可以保证解题和环境生命周期一致。

这样设计的核心原因是：动态环境不是普通文件资源，它有生命周期和平台限制，需要像队列一样被管理。

### 5.8 为什么要有 workspace

每道题都需要一个独立 workspace，用来放题目信息、附件、笔记、脚本、日志和结果。

workspace 的优势是：

- Agent 不会把不同题目的材料混在一起。
- notes、solve、run.log、artifacts 都有固定位置。
- 赛后 writeup 可以直接读取 workspace 材料。
- 出现失败时，人工可以直接进入对应目录排查。
- 历史题可以转化为 cases 或知识库材料。

这样设计的核心原因是：CTF 解题过程依赖大量中间文件，没有 workspace 就很难复盘和沉淀。

### 5.9 为什么要用 Markdown 知识库

CTF 知识需要长期积累，而且需要人能看懂、能修改、能复盘。

Markdown 知识库的优势是：

- 文档可直接阅读，不依赖额外系统。
- 可以保留完整解题链路，而不是只有碎片化片段。
- 方便赛后把 writeup、失败经验、payload 和脚本整理进去。
- 可以按方向分类，让不同 Agent 读取对应知识。
- 后续如果要接 RAG，也可以基于高质量 Markdown 再做索引。

这样设计的核心原因是：项目当前更需要高质量、可维护的知识沉淀，而不是一开始就做复杂检索系统。

### 5.10 为什么需要赛后总结和知识沉淀

如果比赛结束后只留下 flag，项目不会变强。

真正能提高后续解题能力的是：把本次比赛中的题型、漏洞、payload、失败尝试、绕过方法和工具经验沉淀下来。

赛后沉淀的优势是：

- 单题 writeup 可以帮助复盘完整解题过程。
- category summary 可以总结某个方向的共性经验。
- update proposal 可以把新知识进入对应方向知识库。
- cases 可以让类似题在后续比赛中更快被识别。
- 长期积累后，Agent 的参考材料会越来越贴近真实 CTF。

这样设计的核心原因是：CTF 能力提升依赖复盘和积累，知识库闭环比单次解题结果更重要。

## 6. 开发思路

这个项目不是一次性写完的，而是围绕真实 CTF 流程逐步演进出来的。

### 6.1 先确定流程边界

最开始要先明确哪些事情必须中心化，哪些事情可以交给专项 Agent。

中心化的事情：

- 比赛状态管理。
- 题目分发。
- 动态环境数量控制。
- flag 提交。
- 结果记录。
- 赛后总结触发。

交给专项 Agent 的事情：

- 分析题目。
- 写 exploit 或 solve 脚本。
- 整理解题证据。
- 输出结构化结果。

### 6.2 再做状态和 schema

为了让整个流程可控，项目先定义了 challenge、contest、specialist result、dispatch payload、summarize result 等结构。

这些结构不是为了形式化，而是为了让系统知道：

- 当前题目在哪个阶段。
- 应该交给哪个 Agent。
- Agent 应该在哪个 workspace 工作。
- flag 是否已经入队。
- 提交结果是否明确。
- 赛后总结是否完成。

### 6.3 然后实现命令和调度

执行层用 Python 实现核心命令。

这里只保留少量关键命令作为理解入口：

```bash
python -m work.ctf_team.main ctf-start <contest_url>
python -m work.ctf_team.main ctf-status
python -m work.ctf_team.main ctf-dispatch
python -m work.ctf_team.main ctf-submit
```

真实使用时还有自动化入口，例如 `ctf-auto`、`ctf-supervisor`、`ctf-endgame`，但这些本质上都是把上述阶段串起来。

### 6.4 最后靠实战反馈修正

目前很多问题都是实测后暴露出来的，例如不同平台登录不稳定、拿题不完整、提交不流畅、多个 Agent 之间仍有等待。

这些问题不是单纯补 prompt 能解决的，需要继续改 adapter、状态机、runtime、知识库和调度策略。

## 7. 能否提高解题能力

它提高的不是单个模型凭空想出漏洞的能力，而是提高整体 CTF 作战效率和可积累性。

### 7.1 能提高的部分

第一，提高分工效率。

不同方向交给不同 Agent，每个 Agent 使用对应技能和知识库，避免一个通用 Agent 在所有方向上都浅尝辄止。

第二，提高上下文管理能力。

题目信息、附件、target、notes、solve、log 都被放进标准 workspace，后续提交和 writeup 不容易丢材料。

第三，提高提交安全性。

flag 不由各 Agent 随意提交，而是进入统一队列，能减少重复提交、误提交和并发冲突。

第四，提高复盘能力。

每道题的过程可以沉淀成 writeup、case、知识库更新提案，后面再遇到类似题能复用。

第五，提高团队协作稳定性。

哪怕某个 Agent 失败，状态仍然留在系统里，其他 Agent 或人工可以接手，不至于完全丢上下文。

### 7.2 不能直接解决的部分

它不能保证所有题自动解出。

它不能绕过真实平台登录、验证码、反爬、接口差异这些工程问题。

它不能替代高质量知识库和真实比赛经验。

它不能保证 Agent 对新题型、新漏洞、新平台逻辑有足够判断力。

所以这个项目更适合理解为“提高 CTF 解题组织能力和知识复用能力的系统”，而不是“完全自动解题机器”。

## 8. 知识库体系

知识库是这个项目长期提升解题能力的核心。

当前知识库按方向组织：

```text
skills/web/knowledge
skills/pwn/knowledge
skills/reverse/knowledge
skills/crypto/knowledge
skills/misc/knowledge
```

每个方向还会配套：

- `cases/`：历史题和典型案例。
- `update-proposals/`：赛后生成的知识更新建议。
- `knowledge-staging/`：等待合并的知识沉淀。
- `contest-summaries/`：比赛级方向总结。

理想闭环是：

```text
做题 -> 记录 notes/solve/log -> 生成 writeup -> 提炼知识点 -> 进入知识库 -> 下次解题复用
```

这套体系的价值不在于一开始就很强，而在于可以随着比赛持续变强。

## 9. Markdown 知识库与 RAG 的区别及优势

这里比较的是两种知识使用方式：一种是直接维护和读取 Markdown 知识库文档，另一种是使用 RAG 做检索增强。

### 9.1 Markdown 知识库

Markdown 知识库就是把 CTF 经验直接整理成可读文档。

在本项目中，它通常按方向存放：

```text
skills/web/knowledge/*.md
skills/pwn/knowledge/*.md
skills/reverse/knowledge/*.md
skills/crypto/knowledge/*.md
skills/misc/knowledge/*.md
```

这些文档可以直接写清楚：

- 漏洞原理。
- 题型特征。
- 判断方法。
- 利用流程。
- 常见 payload。
- 常见坑点。
- 真实题目案例。
- 失败经验和绕过思路。

### 9.2 RAG 知识库

RAG 通常是把资料切成 chunk，转成向量，放入向量库。模型需要知识时，先根据语义相似度检索片段，再把检索到的片段放进上下文。

RAG 的优势是适合资料量很大、文档很多、人工很难逐个查找的场景。

但在 CTF 场景中，RAG 也容易遇到问题：

- 检索命中的是片段，不一定保留完整 exploit 思路。
- 语义相似不代表解题相关。
- chunk 切分可能把关键上下文拆开。
- 原始资料如果杂乱，RAG 只会更快地检索出杂乱片段。
- payload、环境条件、漏洞链条这类信息很依赖完整上下文。

### 9.3 Markdown 相比 RAG 的优势

第一，知识结构更完整。

CTF 知识经常是一条链路：看到什么特征、判断什么漏洞、尝试什么 payload、失败后怎么绕过、最后怎么拿 flag。Markdown 更容易保留完整过程，而不是只保留几个相似片段。

第二，可读性和可维护性更强。

人可以直接阅读和修改 Markdown，Agent 也可以直接读取。维护它不需要额外的向量数据库、embedding 模型、索引刷新流程。

第三，适合沉淀高质量经验。

赛后可以把 writeup、脚本、失败过程、利用条件整理成明确条目。这样沉淀的是经过筛选的知识，而不是把所有原始资料直接丢进检索库。

第四，来源更清晰。

Markdown 可以直接标注这个知识点来自哪场比赛、哪道题、哪个 writeup、哪个 payload。后续复盘时更容易追踪。

第五，方向隔离更自然。

Web、Pwn、Reverse、Crypto、Misc 的知识体系差异很大。按目录维护 Markdown，可以让对应 Agent 优先读对应方向的知识，减少无关内容干扰。

### 9.4 Markdown 的不足

Markdown 知识库也有明显短板。

- 文档数量变多后，查找成本会上升。
- 如果目录和标题不规范，Agent 可能不知道该读哪篇。
- 对模糊问题和跨方向关联，RAG 的检索能力更灵活。
- Markdown 更依赖人工整理，不能只堆文件。

### 9.5 当前知识库的不足

目前知识库还不够成熟。

主要问题是：

- 覆盖范围还不够广。
- 各方向积累不均衡。
- 真实比赛中的新套路还需要继续沉淀。
- 知识条目质量需要通过更多实战筛选。
- Agent 如何高效检索和使用知识库还需要继续优化。

因此后续需要不断参加 CTF 比赛，或者主动喂历史题、复现题、经典题，让知识库慢慢变厚。

## 10. 当前实测困难

当前项目已经能跑通基本框架，但实测中还有几个明显短板。

### 10.1 不同平台登录拿题不流畅

CTFd、GZCTF、CTF+ 和各种魔改平台差异很大。

登录态、cookie、token、CSRF、验证码、题目接口、详情页结构都可能不同。

这导致现在的自动登录、拿题、补题目详情还不够顺滑，经常需要人工检查和补充。

### 10.2 交题过程不够流畅

不同平台提交接口和返回结果不统一。

有的平台能明确返回 accepted 或 rejected，有的平台只能从页面提示判断，有的平台可能出现 submit_unknown。

所以现在虽然有中央提交队列，但提交体验还没有达到完全稳定。

### 10.3 还不是流水线式解题

理想情况应该是某个 Agent 一完成，结果立刻进入提交队列，马上尝试提交。

目前实测中还存在批次等待问题。五个 Agent 同时启动时，如果其中一个 Agent 先完成，可能会等其他 Agent 完成后才一起进入后续动作，这会拖慢效率。

更理想的方式应该是：

```text
谁先解出 -> 谁先提交结构化结果 -> 谁先进入提交队列 -> 不等待其他 Agent
```

### 10.4 知识库需要长期喂养

知识库不是写好目录就能马上变强。

它需要真实题目、失败经验、writeup、payload、脚本、环境记录不断补进去。

短期内它只能辅助常见题和套路题，长期才可能明显提升整体解题能力。
